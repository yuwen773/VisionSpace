# PostgreSQL 作为唯一业务库：命名、时间与回滚边界

状态：已接受（2026-11-25，随 MySQL → PostgreSQL 18 迁移生效；未经授权不合并 PR、不发布 1.1.0、不部署生产）。

VisionSpace 在首次真实上线前把业务关系库从 MySQL 8 换成 PostgreSQL 18（单实例、单库）。Redis 保留；Chroma → pgvector 下一轮；API / JSON / 前端契约不变。这个决定本身不要求业务代码知道数据库是谁，但下面几件事会长期约束代码与运维，必须写成可核对的契约。

## 1. Schema 只由 Flyway 创建
- 唯一迁移目录 `src/main/resources/db/migration`，基线 `V1__baseline.sql`（31 张业务表 + 种子 + 授权语句），后续只增 `V2+`，不改历史。
- 本机跑 Flyway **13.13.0**（`flyway-maven-plugin` + `flyway-database-postgresql`）：Boot 3.5.16 BOM 管理的 11.7.2 最高支持 PG 17，必须覆盖版本。
- 应用启动不迁移：`spring.flyway.enabled=false`，运行时不引入 Flyway；部署时用 CLI 显式 `migrate` 再 `validate`，失败即中止。
- 禁止用 `psql` 导入基线、用 Docker init 建业务表、或任何应用侧 DDL。Docker init / 部署初始化只允许建角色、建库、装扩展、写库级注释。
- 发布前的例外：V1 还没进任何生产/预发环境，评审期修基线（例如把种子的 `ON CONFLICT` 补上冲突目标）会改变 `V1` 的校验和。**已经跑过旧 V1 的库必须重建**，否则 `flyway validate` 报 checksum 不一致——这正是想要的行为，别手工改 `flyway_schema_history`。首次发布之后 `V1` 冻结。

## 2. 命名与大小写

- 数据库标识符全部 snake_case；Java 实体、JSON、前端契约保持 camelCase。MyBatis Plus 用 `map-underscore-to-camel-case: true` 映射；`QueryWrapper` 里的列名字符串必须手写 snake_case。
- **所有 profile 一律 `map-underscore-to-camel-case: true`**（`application.yml`、`acceptance.yml`、`e2e/application-browser.yml`）。它是「snake_case 列 → camelCase 属性」的唯一开关：任何一处留着 MySQL 时代的 `false`，查询结果就映射不回属性，写接口会以「系统错误」500 的形式炸在业务代码之外。
- 保留字表名 `user` 改为 `app_user`。
- 主键：MySQL 侧 `AUTO_INCREMENT` 的表在 PG 侧一律 `GENERATED BY DEFAULT AS IDENTITY`（共 24 张）。应用仍用雪花 `ASSIGN_ID` 显式写 id，`BY DEFAULT` 让显式值与自增并存；漏掉 IDENTITY 的表会在「调用方不带 id」的写入路径上以 NOT NULL 失败（`resource_access_grant` / `resource_isolation` 就是实例）。`PostgresSchemaConformanceTest` 逐表核对这份清单。
- 文本唯一键按语义选择大小写敏感：
  - 账号：**不区分大小写**，唯一索引建在 `lower(user_account)` 上，查询/登录一律 `lower(...) = lower(...)`；
  - 微信 openid、事件 ID、租约令牌、哈希类（`code_hash`、`pending_key`、`url_hash`）、UUID/客户端幂等键：**区分大小写**，只差大小写就是两个不同的值。
- 原先 MySQL 的 `utf8mb4_unicode_ci` 让所有文本唯一键都不区分大小写；PG 默认区分，因此每个唯一键都要有意识地表态：`PostgresUniqueCaseSemanticsTest` 既按类做行为验证（CI 必须冲突、CS 必须共存），也逐条核对库里全部非主键唯一索引的名称与覆盖列，防止新增或改写唯一键时悄悄改变语义。
- `ILIKE` 只用于模糊搜索，不参与唯一性判定。

## 3. 时间契约

- 存储：`timestamp(0)` **without time zone**，存墙钟时间，秒级精度。不引入 `timestamptz`，不混用。
- 生产：库 `timezone=Asia/Shanghai`，JVM `TZ` 与 `-Duser.timezone=Asia/Shanghai`，JDBC 会话同区；验收/CI 统一 `UTC`。
- API：继续输出无偏移的 `yyyy-MM-dd HH:mm:ss` / ISO local，契约不变。
- 「当前时间」只允许三种写法：
  - 业务 SQL 与列默认值：`statement_timestamp()`（MySQL `NOW()` 是语句开始时间，PG `now()` 是事务开始时间，租约/认领/退避必须保持语句级）；
  - 需要同一事务同一时刻：显式 `now()` 并在注释说明；
  - 禁止 `clock_timestamp()` 作为业务时间（仅诊断可用）。
- 更新时间靠触发器而非列属性：`set_updated_time` / `set_updated_updated_time` / `set_updated_create_time` / `set_updated_gmt_modified` 四个函数，只绑定原本有 `ON UPDATE CURRENT_TIMESTAMP` 的 22 个触发器。触发条件为「行内容变化且调用方未改该时间列」。
- 实体不使用 MyBatis Plus 的 `FieldFill`：项目没有注册 `MetaObjectHandler`，`fill = INSERT/INSERT_UPDATE` 不会填值，只会把未赋值的字段以 NULL 写进 SQL——既绕过列的 `DEFAULT statement_timestamp()`，又让触发器看不到「调用方未改时间列」，最终在 NOT NULL 列上直接失败（`mcp_server.gmt_create` 就是实例）。时间列一律交给数据库默认值与触发器，调用方需要显式时间时自己赋值。
- 已知差异：触发器无法区分「调用方没写该时间列」与「显式写回与旧值相同的值」，两种情况都会刷新。`PostgresTimestampTriggerTest` 固定这一行为。
- 已知差异：空间用量分析的周维度 `period` 由 MySQL `YEARWEEK()`（`202647`）改为 `to_char(create_time,'IYYY-IW')`（`2026-47`）。前端只把它当图表分类标签展示，不解析；但格式与周编号规则（ISO 周 vs MySQL 默认周起始）都与迁移前不同，记录在此避免被当成契约。

## 4. 事务与并发

- 隔离级别显式固定 READ COMMITTED（Hikari `transaction-isolation`），不依赖数据库默认值——PG 默认 RC，MySQL 默认 RR，切换会改变「先读后写」的可见性。
- **事务方法内不得捕获数据库异常后继续执行 SQL**：PG 中任何语句报错都会把事务置为 aborted（`25P02`），后续语句一律失败。需要「冲突即忽略」时用 `INSERT ... ON CONFLICT DO NOTHING` + 影响行数；需要「冲突即翻译」时捕获后必须抛出；需要局部回滚时用 SAVEPOINT。
- `ON CONFLICT` 的冲突目标必须写列清单且与唯一索引一致；**不得用 `rowCount == 2` 区分插入/更新**（PG 插入与 DO UPDATE 都返回 1，DO NOTHING 返回 1/0）。
- `ON CONFLICT DO UPDATE` 的 SET 右侧只看到**旧行**（不是 MySQL 的从左到右），派生列必须用「旧值 + `EXCLUDED`」显式重算。
- 批处理 `UPDATE ... ORDER BY ... LIMIT` 改为 CTE + `FOR UPDATE SKIP LOCKED`，保持「先认领、后处理」，认领带租约且过期可被重新认领。
- 行锁顺序固定为**资源行 → 隔离行 → 统计行**。资源行锁只有 `ResourceLockManager.lockResourceRow` 一个入口，隔离（`ResourceIsolationServiceImpl`）、删除（`PictureDeletionServiceImpl`）、替换/上传（`PictureUploadServiceImpl`）与编辑租约（`PictureEditLeaseCoordinator`）都先取它、再动隔离行或统计行，因此三者之间不会形成锁环。新增写路径必须沿用这个入口，不要自己拼 `FOR UPDATE`。

## 5. 最小权限

- `vision_migrator`：数据库 owner，只用于 Flyway/DDL。
- `vision_app`：仅 `CONNECT`、`USAGE` on schema、表 `SELECT/INSERT/UPDATE/DELETE`、序列 `USAGE/SELECT`；无 CREATE、无 owner、无 DDL。
- 应用、验收、CI 一律以 `vision_app` 连接；`PostgresLeastPrivilegeTest` 要求 `vision_app` 的 `CREATE TABLE`/`ALTER`/`TRUNCATE`/`DROP` 以 `42501 insufficient_privilege` 失败，同时 DML 可用。

## 6. 回滚边界

- 阶段 A（首次真实数据之前）：可以停应用、回退代码、`DROP DATABASE` 并按 Flyway 基线重建。
- 阶段 B（出现第一个真实注册/上传/行为事件之后）：**禁止 drop 生产库**。回滚只能是「从最近 `pg_dump -Fc` 恢复到新库 + 切连接串」或前向修复，并且先在预发演练恢复。
- Flyway 只前向、不写 down migration、`cleanDisabled=true`；MySQL 时代的 `sql/migrations/*-rollback.sql` 归档，不属于 PG 回滚路径。
- 切换点（首次真实写入）必须在发布记录里注明时间。
- 备份口径：每次迁移前 `pg_dump -Fc`，之后每日一次，保留 7 天；`test-postgres-backup-restore.ps1` 验证「备份 → 新库恢复 → schema/数据/授权/触发器都在」，M4 在目标机再演练一次恢复并切连接串到新库。
